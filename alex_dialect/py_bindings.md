# Creating Python Bindings for a Standalone MLIR Dialect

This guide walks through **how the Python bindings for the `cus` dialect were built**, step by step, from zero.

It assumes you already have a working **standalone MLIR dialect** (a
`CMakeLists.txt` that does `find_package(MLIR REQUIRED CONFIG)`, an
`include/<YourDialect>/` with a `.td` file, and a `lib/<YourDialect>/` with
the C++ implementation, building successfully with `cus-opt`-style tool). If
you don't have that yet, that is a separate, earlier step than what this
document covers.

---

## 1. What is a "Python binding," conceptually?

A Python binding is a piece of code that lets Python call into a compiled
C/C++ library — in our case, your MLIR dialect, which is normally only usable
from C++ (writing passes, building IR with `OpBuilder`, etc.).

For MLIR specifically, "Python bindings" means being able to do this in
Python:

```python
from mlir_cus.ir import Context, Module
from mlir_cus.dialects import cus_nanobind as cus_d

with Context():
    cus_d.register_dialects()
    module = Module.parse("... some cus.sqrt / cus.add IR ...")
```

i.e. parse/build/print MLIR IR containing **your custom ops**, run passes on
it, and JIT-execute it — all from Python, without writing any C++.

### Why you can't just "wrap the C++ classes" directly

MLIR's C++ API is full of templates, `ArrayRef`, inheritance hierarchies,
and objects that don't have a stable Application Binary Interface (ABI).
Binding that directly with something like `pybind11`/`nanobind` per-project
would be fragile and would have to be redone by every dialect author.

So MLIR solves this with a **layered architecture**, and understanding these
layers is 90% of understanding how Python bindings work:

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 4:  Python — your dialect's wrapper module              │
│           mlir_cus.dialects.cus_nanobind                      │
│           (hand-written .py + tablegen-generated ops)         │
├─────────────────────────────────────────────────────────────┤
│ Layer 3:  Compiled Python C-extension (nanobind / pybind11)   │
│           CusExtensionNanobind.cpp  →  _cusDialectsNanobind.so│
├─────────────────────────────────────────────────────────────┤
│ Layer 2:  C API  (stable ABI, plain C functions/structs)      │
│           Cus-c/Dialects.h + lib/CAPI/Dialects.cpp (dialect)   │
│           Cus-c/Passes.h   + lib/CAPI/Passes.cpp   (passes)    │
├─────────────────────────────────────────────────────────────┤
│ Layer 1:  Your C++ dialect (what you already built)           │
│           CusDialect.h/.cpp, CusOps.h/.cpp, CusDialect.td      │
└─────────────────────────────────────────────────────────────┘
```

- **Layer 1** is your existing dialect — untouched by binding work.
- **Layer 2 (the C API)** is a thin, stable, `extern "C"` wrapper around
  Layer 1, split into a dialect half (`Dialects.h`/`.cpp`) and a passes
  half (`Passes.h`/`.cpp`). This is the **first new thing you have to
  write** when adding Python bindings — see Step 1 below.
- **Layer 3** is a small `nanobind` (or `pybind11`) C++ file that calls the
  C API from Layer 2 and exposes a Python-callable function
  (`register_dialects`). MLIR's own `ir.py`/`Context`/`Module` classes are
  reused as-is (they come from upstream MLIR) — you don't reimplement those.
- **Layer 4** is plain Python: partly hand-written, partly auto-generated by
  `mlir-tblgen` from the *same* `.td` op definitions you already wrote for
  Layer 1, so the Python op classes (`AddOp`, `SqrtOp`, ...) never drift out
  of sync with the C++ ones.

Everything below explains how to build each layer, and how CMake glues them
together.

## 0. Prerequisites: what must already exist

Before touching Python bindings, this repo already had:

```
include/CusDialect/
  CusDialect.td      # def CusDialect : Dialect { name = "cus"; cppNamespace = "::cus"; }
  CusDialect.h        # #include "CusDialect/CusOpsDialect.h.inc"
  CusOps.td           # def AddOp / Cus_ComputeOp / SqrtOp : Cus_Op<...>
  CusOps.h            # #include "CusDialect/CusOps.h.inc" (GET_OP_CLASSES)
lib/CusDialect/
  CusDialect.cpp       # CusDialect::initialize()
  CusOps.cpp           # op verifiers (e.g. SqrtOp::verify())
```

with the dialect library built via `add_mlir_dialect(CusOps cus)` in
`include/CusDialect/CMakeLists.txt` and `add_mlir_dialect_library(CusDialect ...)`
in `lib/CusDialect/CMakeLists.txt`. If you don't have the equivalent for your
dialect yet, build and test that first (e.g. with a `your-opt` tool), *then*
come back here.

## Step 1 — Write a C API for your dialect (the real "first step")

This is the file beginners often skip, but it is the actual foundation
everything else is built on. MLIR ships a header/macro pair
(`mlir/CAPI/Registration.h`) specifically for this.

Rather than cramming dialect registration and pass registration into one
`Dialects.h`/`Dialects.cpp` pair, this project splits them by
**responsibility**, matching the convention you'll find in
`mlir/lib/CAPI/` and most out-of-tree dialects: a `Dialects.h/.cpp` pair
that only knows about the dialect handle and its extensions, and a separate
`Passes.h/.cpp` pair that only knows about pass registration. Passes tend to
change independently of the dialect definition, and if you ever switch to
tablegen-generated pass C API (`-gen-pass-capi-header/-impl`), you don't
want that generated code tangled up with hand-written dialect code.

### 1a. The dialect C API header: `include/Cus-c/Dialects.h`

```c
#ifndef CUS_C_DIALECTS_H
#define CUS_C_DIALECTS_H

#include "mlir-c/IR.h"
#include "mlir-c/Support.h"
#ifdef __cplusplus
extern "C" {
#endif

MLIR_DECLARE_CAPI_DIALECT_REGISTRATION(Cus, cus);

MLIR_CAPI_EXPORTED void cusRegisterAllExtensions(MlirDialectRegistry registry);
#ifdef __cplusplus
}
#endif

#endif // CUS_C_DIALECTS_H
```

- `MLIR_DECLARE_CAPI_DIALECT_REGISTRATION(Cus, cus)` expands (via the MLIR
  CAPI macros) into a declaration of `MlirDialectHandle mlirGetDialectHandle__cus__(void);`
  — a plain-C, stable-ABI way to hand out "the cus dialect" without exposing
  any C++ type.
- `cusRegisterAllExtensions` is a project-specific extra this dialect
  needed (bufferization/other interface external models) — you only need
  it if your dialect has interface implementations you want reachable from
  Python. Notice pass registration is **not** declared here anymore.

Naming convention: `MLIR_DECLARE_CAPI_DIALECT_REGISTRATION(<CamelCase>, <lowercase>)`
where `<lowercase>` **must match** the `name = "..."` field in your dialect's
`.td` file (here, `name = "cus"` in `CusDialect.td`).

### 1b. The pass C API header: `include/Cus-c/Passes.h`

```c
#ifndef CUS_C_PASSES_H
#define CUS_C_PASSES_H

#include "mlir-c/Support.h"
#ifdef __cplusplus
extern "C" {
#endif

MLIR_CAPI_EXPORTED void cusRegisterAllPasses(void);

#ifdef __cplusplus
}
#endif

#endif // CUS_C_PASSES_H
```

This header only ever grows pass-related declarations. If your dialect has
several passes and you'd rather not hand-write each one's C API, MLIR can
generate this header (and its `.cpp`) straight from your `Pass/PassBase.td`
via `mlir-tblgen -gen-pass-capi-header` / `-gen-pass-capi-impl` — but a
single hand-written `cusRegisterAllPasses()` like above is perfectly fine
for a small number of passes.

### 1c. The dialect C API implementation: `lib/CAPI/Dialects.cpp`

```cpp
#include "Cus-c/Dialects.h"
#include "CusDialect/CusDialect.h"

#include "mlir/CAPI/IR.h"
#include "mlir/CAPI/Registration.h"
#include "mlir/Dialect/Bufferization/Transforms/BufferizableOpInterface.h"
#include "mlir/Dialect/Arith/Transforms/BufferizableOpInterfaceImpl.h"
// ... other MLIR interface headers ...

void cusRegisterAllExtensions(MlirDialectRegistry registry) {
  mlir::DialectRegistry *reg = unwrap(registry);
  mlir::bufferization::registerBufferizableOpInterfaceExternalModels(*reg);
  mlir::arith::registerBufferizableOpInterfaceExternalModels(*reg);
  // ... etc.
}

MLIR_DEFINE_CAPI_DIALECT_REGISTRATION(Cus, cus, cus::CusDialect)
```

`MLIR_DEFINE_CAPI_DIALECT_REGISTRATION(Cus, cus, cus::CusDialect)` is the
*definition* counterpart of the macro used in the header — it's what
actually implements `mlirGetDialectHandle__cus__()` in terms of your real
C++ `cus::CusDialect` class. This one line is the bridge between Layer 1
(C++) and Layer 2 (C API). Notice this file no longer includes any
conversion-pass headers — that's all moved out to `Passes.cpp`.

### 1d. The pass C API implementation: `lib/CAPI/Passes.cpp`

```cpp
#include "Cus-c/Passes.h"
#include "CusDialect/CustomPasses.h"

#include "mlir/Conversion/Passes.h"
// ... other MLIR pass headers ...

void cusRegisterAllPasses(void) {
  mlir::registerConvertMathToLLVMPass();
  mlir::registerArithToLLVMConversionPass();
  // ... etc.
  cus::registerCustomPasses();
}
```

This file has exactly one job: register every pass (upstream conversion
passes plus your own custom ones) so they're reachable by name from
`PassManager.parse(...)` later, whether that's called from C++, C, or (via
Layer 3/4) Python.

### 1e. Wire the C API into CMake: `lib/CAPI/CMakeLists.txt`

```cmake
add_mlir_public_c_api_library(CusCAPI
  Dialects.cpp
  Passes.cpp
  LINK_LIBS PUBLIC
  CusDialect
  MLIRArithTransforms
  MLIRTransforms
  MLIRBufferizationTransforms
  MLIRLinalgTransforms
  MLIRSCFTransforms
  MLIRTensorTransforms
  MLIRReconcileUnrealizedCasts
  MLIRMathToLLVM
  MLIRArithToLLVM
  MLIRSCFToControlFlow
  MLIRControlFlowToLLVM
  MLIRFuncToLLVM
  MLIRMemRefToLLVM
)
```

`add_mlir_public_c_api_library` (from `AddMLIR`) produces a library target
named `CusCAPI` that Layer 3 will link against. Both `Dialects.cpp` and
`Passes.cpp` are listed as sources of the *same* `CusCAPI` target — the
split is a source-file/header organization convention, not a separate
CMake target. List every C++ library either file actually calls into
(your dialect library, plus any transform/conversion libraries used by the
passes you registered).

Don't forget to `add_subdirectory(CAPI)` from `lib/CMakeLists.txt`.

At this point you have a fully working, Python-agnostic C API. You could, in
principle, stop here and call it from any language with a C FFI. Everything
from here on is specifically about exposing it to **Python**.

## Step 2 — Turn on Python bindings support in the top-level `CMakeLists.txt`

```cmake
add_subdirectory(include)
add_subdirectory(lib)
if(MLIR_ENABLE_BINDINGS_PYTHON)
  message(STATUS "Enabling Python API")
  include(MLIRDetectPythonEnv)
  mlir_configure_python_dev_packages()
  if(NOT MLIR_PYTHON_PACKAGE_PREFIX)
    set(MLIR_PYTHON_PACKAGE_PREFIX "mlir_cus" CACHE STRING "" FORCE)
  endif()
  if(NOT MLIR_BINDINGS_PYTHON_NB_DOMAIN)
    set(MLIR_BINDINGS_PYTHON_NB_DOMAIN "mlir_cus" CACHE STRING "" FORCE)
  endif()
  if(NOT MLIR_BINDINGS_PYTHON_INSTALL_PREFIX)
    set(MLIR_BINDINGS_PYTHON_INSTALL_PREFIX "python_packages/cus/${MLIR_PYTHON_PACKAGE_PREFIX}" CACHE STRING "" FORCE)
  endif()
  add_subdirectory(python)
endif()
add_subdirectory(cus-opt)
add_subdirectory(test)
```

Everything about the Python bindings is gated behind the
`MLIR_ENABLE_BINDINGS_PYTHON` CMake option (off by default — you pass
`-DMLIR_ENABLE_BINDINGS_PYTHON=ON` when configuring, see Step 7).

Three variables matter here, and you should pick names deliberately:

| Variable | What it controls | Value here |
|---|---|---|
| `MLIR_PYTHON_PACKAGE_PREFIX` | The **importable Python package name** (`import mlir_cus`) | `mlir_cus` |
| `MLIR_BINDINGS_PYTHON_NB_DOMAIN` | A nanobind-internal namespace string, used to avoid symbol collisions if two nanobind modules end up in the same process | `mlir_cus` |
| `MLIR_BINDINGS_PYTHON_INSTALL_PREFIX` | Where under the build tree the assembled package lands | `python_packages/cus/mlir_cus` |

`mlir_configure_python_dev_packages()` auto-detects your `python3`
interpreter, headers, and (if present) `nanobind`/`pybind11` — this is why
you sometimes need to pass `-DPython3_EXECUTABLE=...` explicitly (see Step 7)
if you have more than one Python installed.

Finally, `add_subdirectory(python)` — this is the directory you create next.

```
├── CMakeLists.txt
├── CusExtensionNanobind.cpp
└── mlir_cus/
    └── dialects/
        ├── CusOps.td
```

Naming pattern to reuse for your own dialect: the top folder under `python/`

## Step 4 — The tiny "Python-binding tablegen" file

`python/mlir_cus/dialects/CusOps.td` — the **entire file**:

```tablegen
include "CusDialect/CusOps.td"
```

That's it — one line. This file is fed to a special `mlir-tblgen` backend
(`-gen-python-op-bindings`), automatically invoked by the CMake function in
Step 5, which walks your **existing** op definitions
(`include/CusDialect/CusOps.td`, with its `AddOp`, `Cus_ComputeOp`, `SqrtOp`)
and generates a Python file `_cus_ops_gen.py` containing one Python class per
op, e.g.:

```python
class SqrtOp(_ods_ir.OpView):
  OPERATION_NAME = "cus.sqrt"
  ...
```

Why not generate straight from `CusOps.td`? Because the Python generator
needs a separate include path/config, and separating this file lets you
selectively expose only some ops, or add Python-only tablegen wrapper
classes later, without touching the "real" op definitions.

You never edit the generated `_cus_ops_gen.py` by hand — it's regenerated
every build.

## Step 5 — `python/CMakeLists.txt`: the glue that assembles everything

This is the file where Layers 2, 3, and 4 all get tied together. Full file:

```cmake
include(AddMLIRPython)

add_compile_definitions("MLIR_PYTHON_PACKAGE_PREFIX=${MLIR_PYTHON_PACKAGE_PREFIX}.")

declare_mlir_python_sources(CusPythonSources)

declare_mlir_dialect_python_bindings(
  ADD_TO_PARENT CusPythonSources
  ROOT_DIR "${CMAKE_CURRENT_SOURCE_DIR}/mlir_cus"
  TD_FILE dialects/CusOps.td
  SOURCES
    dialects/cus_nanobind.py
  DIALECT_NAME cus)

declare_mlir_python_extension(CusPythonSources.NanobindExtension
  MODULE_NAME _cusDialectsNanobind
  ADD_TO_PARENT CusPythonSources
  SOURCES
    CusExtensionNanobind.cpp
  EMBED_CAPI_LINK_LIBS
    MLIRCAPIIR
    MLIRCAPIArith
    MLIRCAPIFunc
    MLIRCAPIMath
    MLIRCAPIMemRef
    MLIRCAPISCF
    MLIRCAPIControlFlow
    MLIRCAPILinalg
    MLIRCAPIBufferization
    MLIRCAPITensor
    MLIRCAPILLVM
    MLIRCAPITransforms
    CusCAPI
)

add_mlir_python_common_capi_library(CusPythonCAPI
  INSTALL_COMPONENT CusPythonModules
  INSTALL_DESTINATION "${MLIR_BINDINGS_PYTHON_INSTALL_PREFIX}/_mlir_libs"
  OUTPUT_DIRECTORY "${MLIR_BINARY_DIR}/${MLIR_BINDINGS_PYTHON_INSTALL_PREFIX}/_mlir_libs"
  RELATIVE_INSTALL_ROOT "../../../.."
  DECLARED_SOURCES
    CusPythonSources
    MLIRPythonSources.Core
    MLIRPythonSources.Dialects.builtin
    MLIRPythonSources.ExecutionEngine
)

add_mlir_python_modules(CusPythonModules
  ROOT_PREFIX "${MLIR_BINARY_DIR}/${MLIR_BINDINGS_PYTHON_INSTALL_PREFIX}"
  INSTALL_PREFIX "${MLIR_BINDINGS_PYTHON_INSTALL_PREFIX}"
  DECLARED_SOURCES
    CusPythonSources
    MLIRPythonSources.Core
    MLIRPythonSources.Dialects.builtin
    MLIRPythonSources.ExecutionEngine
  COMMON_CAPI_LINK_LIBS
    CusPythonCAPI
)
```

Walk through it in order — this is the pattern to copy for any dialect:

1. **`declare_mlir_python_sources(CusPythonSources)`**
   Creates an empty, named "bucket" that other `declare_*` calls below add
   files into. Think of it as an accumulator variable for "all Python-related
   source files belonging to this project."

2. **`declare_mlir_dialect_python_bindings(...)`**
   - `TD_FILE dialects/CusOps.td` → triggers `mlir-tblgen -gen-python-op-bindings`
     on the file from Step 4, producing `_cus_ops_gen.py`.
   - `SOURCES dialects/cus_nanobind.py` → your hand-written wrapper (Step 6).
   - `DIALECT_NAME cus` → used to name/namespace the generated files.
   - `ADD_TO_PARENT CusPythonSources` → registers all of this into the
     bucket from step 1.

3. **`declare_mlir_python_extension(...)`**
   Declares the compiled C-extension module:
   - `MODULE_NAME _cusDialectsNanobind` — **must exactly match** the
     `NB_MODULE(_cusDialectsNanobind, m)` name in the `.cpp` file (Step 6).
   - `SOURCES CusExtensionNanobind.cpp` — the nanobind source file.
   - `EMBED_CAPI_LINK_LIBS` — every C-API library the extension needs at
     link time. Notice `CusCAPI` (your own, from Step 1c) sits alongside
     upstream `MLIRCAPI*` libraries (Arith, Func, Math, SCF, Linalg,
     Bufferization, Tensor, LLVM, Transforms) — list whichever upstream
     dialects/passes your `register_dialects()` function needs (see Step 6).

4. **`add_mlir_python_common_capi_library(CusPythonCAPI ...)`**
   Links *all* the C-API libraries collected across every extension module
   into **one shared library** (avoids duplicate symbols if you ever add a
   second extension module). `DECLARED_SOURCES` also pulls in upstream
   `MLIRPythonSources.Core` (the `ir.py`, `passmanager.py`, etc. that make up
   the base MLIR Python API), `.Dialects.builtin`, and `.ExecutionEngine`
   (needed for JIT execution, used in the tests).

5. **`add_mlir_python_modules(CusPythonModules ...)`**
   The final step: assembles everything declared above (your dialect's
   sources + upstream MLIR core sources) into the actual installable Python
   package tree, and creates the CMake build target `CusPythonModules`
   (you'll build this target explicitly — it isn't part of the default
   `all` target).

## Step 6 — The nanobind extension module

`python/CusExtensionNanobind.cpp` — full file:

```cpp
#include "Cus-c/Dialects.h"
#include "Cus-c/Passes.h"
#include "mlir-c/Dialect/Arith.h"
#include "mlir-c/Dialect/Bufferization.h"
#include "mlir-c/Dialect/ControlFlow.h"
#include "mlir-c/Dialect/Func.h"
#include "mlir-c/Dialect/LLVM.h"
#include "mlir-c/Dialect/Linalg.h"
#include "mlir-c/Dialect/Math.h"
#include "mlir-c/Dialect/MemRef.h"
#include "mlir-c/Dialect/SCF.h"
#include "mlir-c/Dialect/Tensor.h"
#include "mlir/Bindings/Python/IRCore.h"
#include "mlir/Bindings/Python/Nanobind.h"
namespace nb = nanobind;

NB_MODULE(_cusDialectsNanobind, m) {
  auto cusM = m.def_submodule("cus");

  cusRegisterAllPasses();

  cusM.def(
      "register_dialects",
      [](mlir::python::MLIR_BINDINGS_PYTHON_DOMAIN::DefaultingPyMlirContext
             context,
         bool load) {
        MlirContext ctx = context.get()->get();

        MlirDialectRegistry registry = mlirDialectRegistryCreate();
        MlirDialectHandle handles[] = {
            mlirGetDialectHandle__cus__(),
            mlirGetDialectHandle__arith__(),
            mlirGetDialectHandle__func__(),
            mlirGetDialectHandle__math__(),
            mlirGetDialectHandle__memref__(),
            mlirGetDialectHandle__scf__(),
            mlirGetDialectHandle__cf__(),
            mlirGetDialectHandle__linalg__(),
            mlirGetDialectHandle__bufferization__(),
            mlirGetDialectHandle__tensor__(),
            mlirGetDialectHandle__llvm__(),
        };
        for (MlirDialectHandle h : handles)
          mlirDialectHandleInsertDialect(h, registry);

        mlirContextAppendDialectRegistry(ctx, registry);
        mlirDialectRegistryDestroy(registry);

        if (load)
          for (MlirDialectHandle h : handles)
            mlirDialectHandleLoadDialect(h, ctx);

        MlirDialectRegistry extRegistry = mlirDialectRegistryCreate();
        cusRegisterAllExtensions(extRegistry);
        mlirContextAppendDialectRegistry(ctx, extRegistry);
        mlirDialectRegistryDestroy(extRegistry);
      },
      nb::arg("context").none() = nb::none(), nb::arg("load") = true);
}
```

Key points:

- `NB_MODULE(_cusDialectsNanobind, m)` — this name is the compiled shared
  object's module name; it **must match** `MODULE_NAME` in `CMakeLists.txt`
  (Step 5) exactly, or Python's import machinery won't find the right symbol
  table entry.
- Notice this file **only calls the C API** (`mlirGetDialectHandle__cus__()`,
  `cusRegisterAllPasses()`, `cusRegisterAllExtensions()`) — it never touches
  `cus::CusDialect` or any other C++ class directly. That's the whole point
  of Layer 2: the binding code stays simple, stable, and free of C++ ABI
  concerns.
- `register_dialects(context=None, load=True)` is the one function this
  project chose to expose. It (a) registers the `cus` dialect handle
  alongside every upstream dialect the lowering pipeline needs (`arith`,
  `func`, `math`, `scf`, `linalg`, `tensor`, `llvm`, ...), (b) optionally
  loads them eagerly, and (c) applies the bufferization interface
  extensions. You will call this once per `Context` from Python before
  parsing any IR that uses your ops.
- If your dialect needs more than dialect registration exposed to Python
  (e.g. a custom type or attribute needs a Python-constructible wrapper),
  you'd add more `cusM.def(...)` bindings here, using the same C-API-only
  discipline.

## Step 7 — The hand-written Python wrapper

`python/mlir_cus/dialects/cus_nanobind.py` — the **entire file**:

```python
from ._cus_ops_gen import *
from .._mlir_libs._cusDialectsNanobind.cus import *
```

Two lines, and they tie Layer 3 and Layer 4 together:

- Line 1 imports the **tablegen-generated** op classes (`AddOp`,
  `Cus_ComputeOp`, `SqrtOp`) built from Step 4's `.td` file.
- Line 2 imports everything from the compiled extension's `cus` submodule
  (i.e. the `register_dialects` function from Step 6).

After a build, a user does:

```python
from mlir_cus.dialects import cus_nanobind as cus_d

cus_d.register_dialects()   # from the compiled extension
cus_d.SqrtOp                # from the tablegen-generated file
```

Everything else in the final `mlir_cus` package (`ir.py`, `passmanager.py`,
`execution_engine.py`, `_mlir_libs/__init__.py`, ...) is **not** something
you write — it's copied in wholesale from upstream MLIR's
`MLIRPythonSources.Core` / `.Dialects.builtin` / `.ExecutionEngine` by the
`add_mlir_python_modules` call in Step 5. You only ever author the
dialect-specific slice under `mlir_cus/dialects/`.

## Step 8 — Configure and build

```bash
# 1. Use the same Python you'll run your scripts/tests with
source ~/.venv/mlirdev/bin/activate

# 2. Configure, from your build/ directory
cmake -G Ninja .. \
  -DMLIR_DIR=/path/to/llvm-project/build/lib/cmake/mlir \
  -DLLVM_EXTERNAL_LIT=/path/to/llvm-project/build/bin/llvm-lit \
  -DMLIR_ENABLE_BINDINGS_PYTHON=ON \
  -DPython3_EXECUTABLE=$(which python3.10)

# 3. Build your normal tool(s) as usual
cmake --build . --target cus-opt -j $(nproc)

# 4. Build the Python bindings specifically — this is a *separate* target,
#    not part of the default `all`
cmake --build . --target CusPythonModules -j $(nproc)
```

Notes:

- `-DMLIR_ENABLE_BINDINGS_PYTHON=ON` is what triggers everything from Step 2
  onward — without it, `python/` is never even added as a subdirectory.
- `-DPython3_EXECUTABLE=...` (and, if needed, `-DPython3_INCLUDE_DIR`,
  `-DPython_EXECUTABLE`, `-DPython_INCLUDE_DIR`) should be pinned explicitly
  whenever more than one Python is installed on the machine — CMake's
  auto-detection can otherwise pick a different interpreter than the one you
  intend to `import mlir_cus` from later, causing confusing ABI/version
  mismatches.
- The build target name is `<PackageName>PythonModules`
  (`CusPythonModules` here) — it comes from the first argument to
  `add_mlir_python_modules(...)` in Step 5.
- Output lands at `build/python_packages/cus/mlir_cus/` (per
  `MLIR_BINDINGS_PYTHON_INSTALL_PREFIX` from Step 2).

## Step 9 — Use the bindings from Python

This repo has no `pip install`/wheel step — the bindings are consumed
straight out of the build tree by adding it to `sys.path`. Real example,
`test/python/sqrt_test.py`:

```python
import os, sys, ctypes

BUILD_DIR = "/home/mcw/dhinesh/mlir/mlir-train/build"
sys.path.insert(0, os.path.join(BUILD_DIR, "python_packages", "cus"))

from mlir_cus.ir import Context, Module
from mlir_cus.passmanager import PassManager
from mlir_cus.execution_engine import ExecutionEngine
from mlir_cus.dialects import cus_nanobind as cus_d

with Context():
    cus_d.register_dialects()

    module = Module.parse(r"""
    func.func @sqrt_f32(%arg0: f32) -> f32 attributes { llvm.emit_c_interface } {
      %0 = cus.sqrt %arg0 : f32 -> f32
      return %0 : f32
    }
    """)

    pm = PassManager.parse(
        "builtin.module("
        "lower-to-math,"
        "convert-math-to-llvm,"
        "convert-arith-to-llvm,"
        "convert-func-to-llvm,"
        "reconcile-unrealized-casts"
        ")"
    )
    pm.run(module.operation)

    ee = ExecutionEngine(module)
    c_float_p = ctypes.c_float * 1
    arg0 = c_float_p(25.0)
    res = c_float_p(-1.0)
    ee.invoke("sqrt_f32", arg0, res)

    print(f"sqrt({arg0[0]}) = {res[0]}")
    assert abs(res[0] - 5.0) < 1e-5
```

The pattern, generalized:

1. Add `build/python_packages/<name>` to `sys.path`.
2. `from mlir_cus.ir import Context, Module` — the reused, upstream MLIR core
   API.
3. `cus_d.register_dialects()` inside a `with Context():` block — registers
   and loads your dialect (and its dependencies) into that context. Without
   this, `Module.parse` will fail to recognize `cus.sqrt`.
4. Parse/build IR as text or via the `OpBuilder`-equivalent Python API.
5. Run passes with `PassManager` — including `lower-to-math`, your project's
   *own* custom pass, registered in Step 1d/Step 6 and reachable here purely
   because `cusRegisterAllPasses()` ran at module-import time.
6. Optionally JIT and run it with `ExecutionEngine` + `ctypes`, as shown.

## 10. Common pitfalls

- **`ModuleNotFoundError: No module named 'mlir_foo'`** — you built the
  default target but not `<Name>PythonModules`; or you didn't add
  `build/python_packages/<name>` to `sys.path`.
- **Extension fails to import with a symbol/name error** — `MODULE_NAME` in
  `CMakeLists.txt` doesn't match the `NB_MODULE(...)` name in the `.cpp`
  file. They must be identical strings.
- **`cus.sqrt` / your custom op "not recognized" when parsing IR** — you
  forgot to call `register_dialects()` inside the `Context`, or your op's
  dialect handle wasn't added to the `handles[]` array in the extension.
- **Segfaults or missing-pass errors at `PassManager.parse` time** — the
  pass you're referencing wasn't registered; check
  `cusRegisterAllPasses()`/your equivalent actually calls
  `mlir::register<Whatever>Pass()` for it, and that `EMBED_CAPI_LINK_LIBS`
  in `python/CMakeLists.txt` includes the `MLIRCAPI<Dialect>` library that
  pass's dialect belongs to (otherwise you get link errors instead, at
  build time).
- **CMake picks the wrong Python** — always pass `-DPython3_EXECUTABLE=$(which python3.X)`
  explicitly when more than one interpreter is present; a mismatch between
  configure-time Python and runtime Python is the most common source of
  "it built fine but won't import" failures.
- **Packaging as a real `pip install`-able wheel** — this repo (like many
  early-stage out-of-tree dialects) doesn't do this; it's consumed straight
  from the build tree via `sys.path`. If you need a redistributable wheel
  later, look at how upstream MLIR/`torch-mlir`-style projects add a
  `pyproject.toml` that shells out to the same CMake build during
  `pip install .` — that's a packaging concern layered on top of everything
  above, not a replacement for it.
